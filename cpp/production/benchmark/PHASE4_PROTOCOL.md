# Phase 4 protocol — confidence calibration and adaptive tree scheduling

Status: **frozen before Phase 4 measurements**. Revision 1.1. This document, the workload manifest, runtime/benchmark sources, fitter, runner, and analysis implementation are hashed and recorded in immutable `freeze.json` before any locked-evaluation observations or outputs are opened for analysis. All Phase 4 work was performed in an isolated workspace; the shared publication checkout remained read-only during the experiment. **Publication note:** this repository copy replaces host-specific paths with portable labels; the hashes in the freeze metadata identify the experiment-time source text.

## Objective and scope

Test whether verifier-derived acceptance outcomes and candidate-side draft features can support a calibrated confidence estimate and a per-pulse adaptive scheduler for Pulsar's exact bounded candidate tree. The experiment reuses the Phase 3 CPU-only TinyStories GGUF fixture, target/draft models, two-thread setting, batch sizes 1 and 2, and sampling law. This is one tiny-model x86_64 fixture experiment, not a general-model or production-performance claim.

Phase 3 remains the reference: its fixed tree measured 0.317x autoregressive throughput at batch 1 and 0.151x at batch 2; llama.cpp built-in `draft-simple` measured 0.699x and 0.795x. A Phase 4 win over a fixed tree alone is not an overall acceleration claim.

## Group split and leakage controls

The 24 prompts are fixed in the manifest. Each prompt is one independent topic/context group, and no prompt/context is shared across splits. Calibration groups C01–C08 are used only to fit confidence models. Tuning groups T01–T08 are used only to select fixed baselines and estimate action costs. E01–E08 are locked evaluation groups. Their prompt texts are part of the predeclared manifest, but no E-group model outputs, acceptance rows, timing rows, or metrics may be read to change the model, calibrator, scheduler, baseline, workload, or analysis. All evaluation methods must finish before evaluation outputs are opened for analysis.

## Calibration, adaptation, and scheduling (separately testable)

1. **Candidate-side features.** At each verifier decision, log draft-law maximum probability, top-1/top-2 probability margin, normalized entropy, and proposal-token probability. Also log the pulse-root draft-law maximum probability, root margin, and root normalized entropy. The prediction feature vector is the pulse-root triple only; it is available before a tree action is selected and contains no target logits, target probabilities, generated output text, or verifier result.
2. **Labels.** Retain the verifier's exact Boolean `accepted` outcome for each proposed token. Also label whether that decision would continue to a deeper verifier position (`continued`): accepted, nonterminal, and the proposal token has a retained child. The final possible depth of a tree has no continuation label because no deeper position exists. Both labels are generated by the exact verifier; no label is inferred from output text.
3. **Calibrator.** Fit deterministic L2-regularized logistic models using C groups only, separately by batch size, branching factor, and 1-based verifier depth. Fit an acceptance model and a continuation model, using the root candidate-side feature triple. Standardize each feature with its C-split mean and population standard deviation (scale floor 1e-6). Minimize mean logistic negative log-likelihood plus `0.5 * ||slopes||^2` (L2 strength 1.0; intercept unpenalized) using deterministic Newton-Raphson with partial-pivot Gauss-Jordan, at most 100 steps and coefficient-change tolerance 1e-10. For each branching factor, fit from only its largest predeclared tree depth to avoid duplicate calibration rows from overlapping action configurations. Store coefficients and training-data hashes. Report Brier score and 10-bin reliability tables by depth and workload, including the scheduler-selected distribution on locked evaluation rows.
4. **EMA update.** Keep a separate per-request EMA state keyed by (branching factor, 1-based depth). It starts unseen and is updated after each verifier pulse using that pulse's available `continued` labels with alpha 0.20. The request-local state resets at each new prompt/seed run. This is a lightweight online update, not model training or a cross-request bandit.
5. **Scheduler.** For each available action and depth, combine the current calibrator continuation prediction with the EMA estimate as `0.5 * calibrated + 0.5 * EMA` when that EMA has observations; otherwise use the calibrated prediction. Estimate tokens emitted per pulse as `1 + p0 + p0*p1 + ...`, truncated by remaining output/context positions. Divide by the per-pulse generation cost measured for that action on T groups: the median, across tuning batches, of generation-wall-time in milliseconds / verifier-pulse count, by batch size and action. Choose the action with the highest predicted tokens/ms; ties prefer fewer actual tree nodes, then shallower depth, then lower branching. Retain a per-request pulse index so action frequencies count scheduler decisions, not per-depth trace rows. Only past verifier results and current draft-side root features can influence the next action. No target-side information from the current pulse is used to schedule that pulse.
6. **Policy selection.** The model family, feature set, L2 strength, optimizer, EMA alpha/mix, action grid, utility, tie-break, and bootstrap procedure are frozen here. No scheduler hyperparameter search is permitted on E groups. Fixed-tree and built-in-chain baseline configurations are selected using T groups only.

## Tuning and freezing

For each batch size independently, run autoregressive decoding; built-in `draft-simple` for n_max 2, 4, 6; and all three fixed-tree candidates. Select the fixed tree and built-in chain with the highest median aggregate generated tokens/second across T-group batches, tie-breaking toward fewer actual tree nodes / lower n_max. Select the adaptive coefficients from C data and timing-cost table from T data. Before the first locked-evaluation run, create immutable `freeze.json` containing model and source hashes, prompt-manifest/protocol/fitter/runner/analysis hashes, CTest status, sampling/workload settings, selected baseline settings, calibrator coefficients/training hashes, per-action tuning costs, adaptive policy constants, runtime/build/host identity, bootstrap plan, and timestamp. If any material field changes, do not use existing evaluation data; issue a new protocol revision and new locked groups.

## Evaluation and comparisons

On E01–E08 and all locked roots, run autoregression, the tuning-selected built-in chain, adaptive scheduling, and all three fixed-tree candidates (the tuning-selected fixed tree is one of these). Within each batch size, method order is shuffled deterministically using Python `random.Random(10000 + batch_size)`; the actual order is retained. All methods must complete before the analysis script opens any evaluation raw record, generated output, observation, or metric. Pair methods by `(seed_root, tuple(batch_prompt_ids))`. Keep raw observations append-only. Compare throughput and latency for each batch size separately. Report completions, aggregate tokens/s, total batch time, request p50/p95 latency, process RSS, estimated live KV, work counters, tree nodes/pulses, tree build/verification cost, chosen-action frequencies, and acceptance/continuation features/labels.

The **offline fixed-action oracle upper bound** is descriptive: after evaluation is unlocked, for each locked `(seed_root, prompt-group batch)` choose the fastest measured fixed-tree action among the three predeclared candidates, then aggregate its throughput. Ties prefer fewer actual tree nodes, then shallower depth, then lower branching. It uses evaluation outcomes and is expressly not a deployable policy, not a confirmatory winner, and not a causal estimate of an online scheduler's counterfactual choices. It upper-bounds fixed-action selection on these observed group batches only.

## Statistical analysis and pass criteria

- Use 10,000 paired cluster bootstrap draws with fixed analysis seed 5555. Use the same seeded cluster-resampling stream for all method comparisons within a batch size. Resample context-group clusters with replacement, preserving all paired seed roots and all methods within each cluster. For batch size 1, clusters are individual E groups; for batch size 2, clusters are the predeclared adjacent pairs `(E01,E02)`, `(E03,E04)`, `(E05,E06)`, `(E07,E08)`.
- Throughput ratio is the ratio of total generated tokens / total batch wall time in each resample. Report percentile 95% intervals. For latency, resample the same matched clusters and compute p95 per-prompt latency ratios and percentile intervals.
- **Phase 4 performance win gate:** exactness checks pass; on the claimed workload, the paired 95% CI for adaptive/fixed-tree throughput lies entirely above 1.00; and the upper bound of the paired 95% CI for adaptive/fixed-tree request p95 latency ratio is at most 1.10 (predeclared 10% non-inferiority margin). Report each batch size separately; a pass on one batch size does not imply a pass on the other. A win over the fixed tree is not an overall acceleration claim unless the adaptive method also beats autoregressive decoding with a paired 95% throughput interval wholly above 1.00 and the same p95 latency non-inferiority condition.
- Calibration quality or a calibration improvement is not a performance pass. Any failed or inconclusive condition is reported as such.

## Exactness and scope limits

The adaptive scheduler may alter only the bounded tree action for a future pulse. It cannot change the target distribution, proposal-law preservation, exact acceptance ratio, residual replacement, EOS handling, or KV-prefix rules. Run the inherited production verifier/tree tests plus new tests for calibrator, EMA, legal scheduling, observation capture, and adaptive exactness on deterministic synthetic laws/fake models, as well as deterministic Python fitter/analysis checks, before any measurements. Exactness refers to the implemented target sampling law, not token-for-token equality under different random-number consumption. No model training/fine-tuning, quantum mechanism, GPU test, or general speedup claim is in scope. Preserve Phase 1–3 contracts, source evidence, and reports unchanged.
